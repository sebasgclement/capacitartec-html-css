Feature Queries

Las media queries preguntan por el tamaño de pantalla. @supports pregunta algo distinto: "¿este navegador entiende esta propiedad de CSS?"

¿Qué problema resuelve?

Cuando usás una propiedad de CSS muy nueva, no todos los navegadores la soportan todavía (o alguien en el aula tiene uno desactualizado). Sin ningún control, el navegador viejo simplemente ignora la propiedad que no entiende — a veces eso está bien, y a veces deja el layout roto porque esa propiedad era la única que sostenía el diseño.

@supports te deja preguntar por adelantado: "si el navegador soporta tal propiedad con tal valor, aplicale este bloque de reglas". Así podés dar un CSS base que funciona en cualquier navegador, y sumar una mejora solo donde hay soporte real — el mismo espíritu de "sumar, no corregir" del tema anterior.

Sintaxis mínima

/* Base: funciona en cualquier navegador */
.lista { display: flex; flex-wrap: wrap; gap: 12px; }
.item { flex: 1 1 240px; }

@supports (display: grid) {
  .lista { display: grid; grid-template-columns: repeat(auto-fill, minmax(220px, 1fr)); }
}

Se puede combinar con and, or y not:

@supports (display: grid) and (gap: 1rem) { ... }
@supports not (display: grid) { ... }             /* la negación: para el fallback explícito */
@supports (display: flex) or (display: grid) { ... }

El valor importa, no solo la propiedad: @supports (display: grid) pregunta específicamente por el valor grid, no por si la propiedad display existe (existe en todos lados).

Resultado

Hoy prácticamente todos los navegadores soportan Grid, así que vas a ver la versión con @supports. Cambiá la condición a @supports (display: masonry) (que casi ningún navegador soporta todavía) para ver el fallback de Flexbox en acción.

Errores comunes

  • Usar @supports para propiedades que ya son universales Envolver flexbox en un @supports hoy es innecesario: lo soportan todos los navegadores relevantes desde hace años. Reservalo para features realmente nuevas.
  • No escribir la base sin @supports @supports es para sumar una mejora sobre una base que ya funciona. Si el bloque con la mejora es el único CSS que existe, un navegador sin soporte se queda sin estilos, no con un fallback razonable.
  • Confundir @supports con @media Son dos preguntas distintas: @media pregunta por el entorno (tamaño de pantalla, preferencias), @supports pregunta por las capacidades del navegador. Se pueden anidar, pero no son intercambiables.
  • Poner un valor inválido en la condición @supports (display: bloque) (con un valor que no existe) siempre da falso, silenciosamente. Si el bloque nunca se aplica, revisá que la propiedad y el valor estén bien escritos.

Cuándo NO usarlo

✔ @supports

Features de CSS muy nuevas (como subgrid o animation-timeline, que ya viste) donde te interesa dar un fallback razonable a navegadores viejos.

✘ Sin @supports

Para features con soporte universal desde hace tiempo (flexbox, grid básico, variables CSS). Envolver todo "por las dudas" es ruido innecesario.

Mini-ejercicio

  2. Probá @supports not (display: grid) para escribir el caso "sin soporte" de forma explícita, en vez de depender del orden del CSS.
