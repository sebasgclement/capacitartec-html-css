Animaciones y promesas

El cierre del módulo: cuando la animación tiene que reaccionar a JavaScript (y JavaScript tiene que esperar a que termine), entra la Web Animations API.

¿Qué problema resuelve?

Todo lo anterior se declaró en CSS. Pero a veces la animación depende de datos que solo existen en JavaScript (la posición de un drag, el resultado de una acción), o necesitás encadenar varios pasos donde cada uno espera a que el anterior termine antes de arrancar.

Hacer eso con setTimeout y clases de CSS funciona, pero se vuelve difícil de leer apenas hay 2 o 3 pasos encadenados. La Web Animations API (element.animate()) te da un objeto Animation con una propiedad .finished que es una promesa: se resuelve cuando la animación termina. Con await, encadenar pasos se lee de arriba hacia abajo, en el orden en que realmente pasan.

Sintaxis mínima

const animacion = elemento.animate(
  [{ transform: "translateX(0)" }, { transform: "translateX(200px)" }], // keyframes
  { duration: 500, easing: "ease-out", fill: "forwards" }               // opciones
);

await animacion.finished; // se resuelve cuando termina

Encadenar pasos en secuencia, cada uno esperando al anterior:

async function secuencia(el) {
  await el.animate([{ opacity: 0 }, { opacity: 1 }], { duration: 300 }).finished;
  await el.animate([{ transform: "scale(1)" }, { transform: "scale(1.2)" }],
                    { duration: 300, fill: "forwards" }).finished;
}

Correr dos animaciones en paralelo y esperar a que terminen las dos:

const a = el.animate([...], { duration: 500 });
const b = otroEl.animate([...], { duration: 500 });
await Promise.all([a.finished, b.finished]);

El objeto Animation también se controla en vivo: .pause(), .play(), .cancel(), .finish(), y se le puede leer/escribir .currentTime y .playbackRate.

Errores comunes

  • Olvidar fill: "forwards" Sin eso, apenas termina la animación el elemento vuelve a su estado original — igual que con @keyframes sin animation-fill-mode. Si el resultado final "desaparece" de golpe, es esto.
  • No guardar la referencia al Animation para poder cancelarlo Si el usuario hace click varias veces seguidas sin guardar (y cancelar) las animaciones anteriores, quedan corriendo varias a la vez compitiendo por el mismo elemento. Guardá cada Animation en un array y cancelalas antes de arrancar una nueva, como en el ejemplo.
  • Confundir await a.finished con esperar el tiempo real Si se llama a.cancel() antes de que termine, la promesa .finished se rechaza en vez de resolverse. Un código de secuencia sin manejo de ese rechazo puede tirar un error no capturado en consola.
  • Animar propiedades que no acepta la Web Animations API igual que CSS La sintaxis de los keyframes en JS es casi idéntica a CSS, pero algunos shorthands se comportan distinto. Cuando algo no anima como esperás, probar la propiedad "larga" (por ejemplo backgroundColor en vez de background) suele resolverlo.

Cuándo NO usarlo

✔ Web Animations API

Animaciones que dependen de datos calculados en JS, que necesitan encadenarse en secuencia, o que hay que pausar/cancelar/revertir según lo que haga la persona.

✘ CSS puro (transition / @keyframes)

Todo lo que se puede describir de antemano y no depende de lógica: un hover, un loop, un reveal simple. Es más simple de escribir y el navegador puede optimizarlo mejor.

document.getElementById("par").onclick = async () => {
  stopAll();
  const a = el.animate([...], { duration: 500, fill: "forwards" });
  const b = el.animate([...], { duration: 500, fill: "forwards" });
  running.push(a, b);
  await Promise.all([a.finished, b.finished]);
  console.log("terminaron las dos");
};

Promise.all se resuelve recién cuando todas las promesas de la lista se resolvieron — exactamente lo que hace falta para saber "ya terminaron ambas animaciones", sin importar cuál termine primero.
