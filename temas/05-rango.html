Rango de animaciones

La versión sin JavaScript del tema anterior: que el scroll mismo sea quien "conduce" la animación, con CSS puro.

¿Qué problema resuelve?

En el tema anterior, IntersectionObserver avisa una vez cuando el elemento entra en pantalla, y de ahí en adelante la animación corre sola con su propia duración en segundos. No sigue el scroll: sigue el reloj.

animation-timeline cambia la fuente del tiempo: en vez de que la animación avance con los segundos, avanza con el progreso del scroll. Si dejás de scrollear, la animación se congela exactamente donde estaba. Si scrolleás para atrás, retrocede. Es la misma sintaxis de @keyframes que ya conocés, solo que el reloj es distinto.

Sintaxis mínima

@keyframes growspin {
  0%   { transform: scale(.6) rotate(0deg); opacity: .4; }
  100% { transform: scale(1.2) rotate(270deg); opacity: 1; }
}

.caja {
  animation: growspin linear both;
  animation-timeline: view();       /* el reloj: el scroll del elemento en el viewport */
  animation-range: entry 10% cover 80%; /* qué tramo del scroll usa */
}

animation-timeline: view() ata la animación a la posición del elemento dentro del viewport a medida que se scrollea. animation-range recorta qué tramo de ese recorrido cuenta: entry 10% es "cuando el elemento lleva 10% entrando", cover 80% es "hasta que cubre el 80% del viewport".

Como es una API nueva, conviene envolverla en un @supports y tener un plan B para navegadores viejos: 

@supports (animation-timeline: scroll(block)) {
  .caja { animation: growspin linear both; animation-timeline: view(); }
}

Resultado (scrolleá adentro)

Scrolleá despacio dentro del panel de resultado: la caja crece y gira exactamente al ritmo de tu scroll, no de un reloj. Probá cambiar animation-range a entry 40% cover 60% para que el tramo activo sea más corto y el efecto se sienta más rápido.

Errores comunes

  • Confundir view() con scroll() view() sigue la posición del elemento dentro del viewport (lo que usamos acá). scroll() sigue el progreso del scroll de todo un contenedor. Son dos casos de uso distintos con nombres parecidos.
  • Olvidar el fallback Es una API relativamente nueva. Sin @supports ni un plan B, en un navegador que no la soporte el elemento se queda estático en su estado inicial (scale(.6), medio transparente) para siempre.
  • No usar both en el fill-mode Sin fill-mode: both, fuera del rango activo el elemento puede no mostrar ni el primer ni el último frame correctamente.
  • Rangos tan angostos que se sienten abruptos Un animation-range muy corto (por ejemplo entry 45% cover 50%) hace que la animación pase casi de golpe. Para un efecto que se note, conviene un tramo de al menos 30-40% del recorrido.

Cuándo NO usarlo

✔ animation-timeline

Efectos donde el scroll mismo es protagonista: una barra de progreso de lectura, un elemento que crece a medida que avanzás, un fondo que cambia de color según cuánto scrolleaste.

✘ IntersectionObserver + transition

Si el efecto es simplemente "aparecer una vez al entrar" (el caso del tema anterior), y necesitás soporte garantizado en cualquier navegador, sin plan B.
